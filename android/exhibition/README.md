# OpenBuy 展会试衣镜 Android

应用版本 **0.6.10 / versionCode 25**，包名 `ai.openbuy.exhibition`。启动时自动选择设备支持的镜端：WebView 111 及以上打开最新 V1.1 网页；旧 WebView 自动进入原生 XMAX 镜端。旧设备可选择由 Linux 或安卓本机识别手势，主视频始终通过安卓原生 RTC 直接连接 XMAX。

## 安装使用

1. 安装 `OpenBuy-展会试衣镜-0.6.10.apk`，允许摄像头权限。需要 Android 9 或更新版本；WebView 74 设备自动使用原生兼容入口，无需升级系统 WebView。旧入口支持 XMAX；Decart 仍需 WebView 111 及以上。
2. 首次显示四位绑定码，在 V1.1 工作人员后台绑定对应智能镜。同签名覆盖升级沿用原来的安装身份与绑定；不同构建机的 debug 签名不能直接覆盖旧包。
3. 在后台配置该镜的供应商密钥与素材，点击“开始体验”才启动生成。永久密钥不写入 APK。

默认镜端为 `https://xuxin.local:10202/v1.1/exhibition/screen`，后台为 `http://xuxin.local:10101/`。大屏和 Ubuntu 后台电脑须在同一局域网，云端生成还需互联网。新设备网页更新后重新连接即可；旧设备的原生界面和安卓本机手势判断脚本随 APK 更新，Linux 模式的手势推理与判断随后台更新，服装与后台设置仍实时同步。

网页入口长按左下角“设备”、原生入口长按 Logo 可修改镜端网址。原生入口通过系统 DNS、局域网 NSD 服务和已有备用 IP 解析后台；Ubuntu 同时广播 `xuxin.local` 地址和 `Miror-xuxin` 服务，避免与原 Mac 冲突。默认地址迁移保留镜编号，自定义地址不变。HTTP 10101 与旧 HTTP 10200 镜端地址自动使用同主机 HTTPS 10202。

debug 包仅对指定局域网域名信任随包 CA 公钥，不跳过 TLS 或主机名验证。后台重建 CA 后需重新打包。直接使用 IP 地址时，证书仍须包含该地址，且设备需信任对应 CA。

## 摄像头采集分辨率

0.6.5 原生入口增加「设备设置 → 采集分辨率」。先停止生成，长按 Logo，选择摄像头及分辨率，预览成功后保存。下拉框只列出该摄像头通过 Android 系统报告的支持档位，支持时可选 **3840×2160 · 4K**；默认「自动」优先选择 1080p 范围内最大的可用尺寸，仅支持更大尺寸时选择其中最小档。无法读取能力时沿用 704×1280。

预览状态显示 RTC 返回的「实际」采集宽高；驱动降档时同时显示请求尺寸。配置保存在本机，覆盖升级及会话重连保留。切换摄像头后，如果已选分辨率不再支持，会提示重新选择。当前请求 24 帧/秒，实际帧率由摄像头、驱动与设备负载决定。

采集与模型编码尺寸独立：4K 原始画面用于采集，发送给 XMAX 前仍根据实际画面比例，按当前模型支持的像素数及 32 倍数规则缩小。4K 采集不代表模型以 4K 生成。实机须核对「实际 3840×2160」并检查预览、生成和手势同时运行的流畅度。

## 摄像头画面方向

先停止生成，在原生镜端长按 Logo，进入「设备设置 → 安装方向」，选择默认、顺时针 90°、旋转 180°或逆时针 90°。调整时直接查看摄像头预览，人物朝上后保存，再开始体验。取消不保存；方向保存在当前安卓设备，覆盖升级保留。后台打开的「摄像头检测」也提供相同选项。

预览与模型输入共用此安装方向。修正在 RTC 采集端设置，发送视频沿用同一角度。手势抽样沿用 RTC 帧的旋转信息，避免重复旋转。图片输入模式不应用摄像头角度。旋转与旧设备传感器信息的实际组合仍须在对应大屏验收。

0.6.2 根据 RTC 返回的实际帧宽高和旋转信息确定相机输入比例，并在连接前统一编码和生成请求尺寸，修正此前旋转后仍使用固定竖向尺寸的遗漏。不会再次旋转生成结果。验证时需同时检查原始预览与生成画面中的人物比例，覆盖默认、90°、180°和270°；本地回归与构建不能替代具体安卓大屏的摄像头和云端生成验收。

0.6.3 在相机采集与 XMAX 编码之间增加方向适配：按校正后的实际宽高选择 RTC 固定横向或竖向模式，让 SDK 在编码前处理旋转并将旋转标记归零。每次重新采集先恢复自适应模式以读取真实尺寸，图片和视频文件输入会清除相机方向校正。该适配沿用设备设置中的安装角度，不会根据人物动作自动猜测或改变方向。

升级时移除旧「XMAX输入方向」设置。原先跟随摄像头或两项相同的设备直接保留安装角度；两项冲突时暂停开始体验，提示进入设置校准。工作人员检查本地预览、调整安装方向并保存后解除提示；取消或预览失败不会解除。该本地预览不能证明远端编码或生成画面方向正确。

现场验收须使用四角不同标记的非正方形画面，覆盖 0°、90°、180°、270°和前后镜像，核对实际接收解码像素、rotation 与模型宽高。JVM 回归覆盖像素转换、尺寸和 RTC 参数；无物理设备时不宣称编码像素或 XMAX 接收已验收。

## 两台旧设备对比

在原生入口长按 Logo，使用现有设备设置中的“手势识别”选择 **Linux 电脑**（默认）或 **安卓本机**。选择会保存在本机，设备绑定不变。应先停止体验再切换模式，分别在两台设备上用相同摄像头、位置、光照与手势参数比较。

| 模式 | 识别位置 | 额外局域网传输 | 主要验收点 |
| --- | --- | --- | --- |
| Linux 电脑 | Ubuntu 上每设备独立的 MediaPipe CPU 人体、手部模型及 V1.1 检测器 | 摄像头抽样 JPEG，跟随后台 480/720/960 像素（默认 720）、5–30 帧/秒（默认 15）；优先质量 82，每帧最多 256 KiB | 双手任选有效手势、持续举手防重复，以及两台同时使用时的时延、丢帧与恢复 |
| 安卓本机 | 安卓原生 MediaPipe 手部模型，离线执行 APK 内的 V1.1 检测器 | 无手势画面上传 | 旧安卓 CPU 的速度、发热及主视频是否受影响 |

两种模式均复用 RTC 捕获的画面，不占用第二路摄像头。主视频、云端生成画面和音视频连接均不经过 Linux 转发。Linux 手势帧仅在内存中处理，不保存画面；每台设备最多一帧在途，后来的繁忙帧直接丢弃，不补发。新连接或重试后先收手，避免仍举着的手被当成新动作。

0.6.9 起网页、Linux 和安卓本机共用同一规则：两只手入镜时分别识别，任一只符合已启用的手势即触发一次；两只同时符合也只触发一次，持续举着不重复。人体未检出、手腕归属不明或多人入镜不会单独否决有效手势。Linux 与网页的人体姿态仍可辅助判断下放；安卓本机保留仅手部模型，通过握拳或收手观察释放。

所有手均未检出并持续达到收手时长（`palmReleaseMs`，默认500ms）后自动复位，不依赖人体姿态是否仍在或变化；短暂漏检不会立即重触发。

Linux 侧需先按 [运行时说明](../../runtime/gesture/README.txt) 安装隔离 Python 环境，然后沿用 `miror-preview.service` 启动服务。默认最多两路识别会话。安装依赖不修改系统 Python，也不需要 XMAX 密钥。Linux 模式故障时显示简短的手势重试入口，手动选衣仍可用；不会暗中切换模式而影响对比结论。

## 最新镜端行为

- 0.6.9 统一双手识别：任一只手符合即触发，两只同时符合只执行一次。安卓本机需安装新 APK 才能更新内置检测器；设备绑定和识别模式保留。
- 0.6.8 将 Linux 手势抽样尺寸、帧率、收手及再次抬手提示与网页对齐，新后台兼容旧 APK 并提供人体姿态识别。
- 0.6.7 将体验中的停止操作移至视频下方边框，与手势状态并排显示为小方块图标；正在停止时禁用。开始、继续及恢复操作保留原位置。
- 持续展掌只换一次，收手后再抬手才能再次触发。
- 命令提交、素材准备、连接与服务端生成期间丢弃手势，不排队、不补执行；有效收手仍用于解除手势锁定。
- 点击选衣、翻页笔方向键和后台选衣仍可使用；手势忙碌拦截不会取消手动操作。原生 SDK 条件更新保持串行。
- 收到服务端切换确认后恢复手势；SDK 没有逐套服装画面完成信号，实际画面可能稍后更新。
- 两种入口均保留摄像头选择、后台远程检测、素材抽屉与皮肤。旧设备从 RTC 已捕获的画面抽样，不另开第二路摄像头；最多检测两只手，两种识别模式均逐手判断并共用动作防重复锁。
- 安卓本机推理保持最多 10 帧/秒、输入长边最多 640 像素；Linux 从 RTC 抽样到上传均跟随后台 480/720/960 像素、5–30 帧/秒，默认 720 像素与 15 帧/秒，不放大小尺寸原始画面。JPEG 优先质量 82，超出 256 KiB 时逐级降低质量并保留尺寸；仍超限则丢弃。更改抽样设置立即使旧帧失效，不影响 XMAX 主视频采集或编码。繁忙帧和超过 800ms 的迟到结果直接丢弃，实际帧率取决于设备与网络。
- 原生安装身份通过同源接口提供给镜端，网页不持有永久供应商密钥。设备自启动、系统 kiosk 和 USB 驱动由大屏系统配置。
- 原生端与网页端共用服务端 `catalog.looks` 可用目录和 `catalog-v2` 协议。开始与换装只提交素材 ID、内容版本及操作身份，由后台解析并绑定持久引用；原生端不再做 1.5 秒准备预查或重复绑定。目录更新即时反映在可选列表，`activeLook` 保持正在使用的旧版本，直至下一次选择。旧后台缺少目录时明确提示升级；网络、素材未准备、版本变化和供应商错误保留各自错误类型与原因。MoX 仅下载本地原图作为输入画面。
- 续接先取得后台计划，再释放旧 RTC 和确认旧凭证停止，最后提交续接。取得计划前的临时网络错误或素材切换冲突保留当前画面，在后续心跳重试；租约与凭证硬到期仍独立约束连接。

## 构建与验证

需要 JDK 17、Android SDK 37.0、build-tools 36.0.0。项目使用 AGP 9.1.1、Gradle 9.3.1，minSdk 28、targetSdk 35。

```sh
# 在仓库根目录，使用项目 Node.js 运行时生成并核对共享手势脚本
node scripts/build-android-gesture.mjs
node scripts/build-android-gesture.mjs --check
cd android/exhibition
sh scripts/build-local.sh assembleDebug lintDebug --max-workers=2
sh scripts/test-native.sh
```

`build-local.sh` 仅为当前进程设置工具链路径，不改全局 shell，不自动接受许可。默认兼容 Mac 工具链与 Ubuntu 的 `~/.local/share/openbuy-android/{jdk-17,sdk}`，也可设置 `JAVA_HOME`、`ANDROID_HOME`、`GRADLE_USER_HOME`。

输出 `app/build/outputs/apk/debug/app-debug.apk`。debug 签名由构建机的本地 keystore 决定；覆盖旧包需要相同签名。正式发布需另行配置长期签名，不应卸载已有绑定的包来绕过签名不匹配。

原生 JVM 测试使用隔离网络与供应商替身，不消耗真实额度，覆盖原生流程、上传所有权、帧过期、迟到结果和 NSD。网页手势集成测试使用真实检测器、Hook 和 Kiosk，仅模拟摄像头推理和网络。`tests/nativeGestureRuntime.test.ts` 同时校验 APK 内脚本与当前 TypeScript 源码完全一致；旧 Chromium 和 Android 的验证见 [手势运行时](docs/native-gesture-runtime.md)。服务端协调器、HTTP 边界和真实模型分别有隔离测试，模型性能结果不包含安卓编码与局域网往返时间。实际两台 ARM 大屏摄像头与云端画面仍须实机验收。

`uiPreview` 仅用于静态界面截图，包名后缀 `.uipreview`，不作为摄像头、手势或云端生成的验收结果。

## 保留的原生 SDK

官方来源：https://github.com/XingMai/XmaxSDK-Android ，固定 commit `14ed6e1327f82c58bb17ea93910d301caee80aea`。MIT 许可证保留在 `vendor/xmax-sdk/LICENSE`，`UPSTREAM.json` 记录源码和 JNI SHA-256。

SDK 源码调整国内/国际两个 API 根地址，并补充 RTC 摄像头枚举和按设备 ID 选择；具体差异见 `vendor/xmax-sdk/LOCAL_CHANGES.md`。JNI 来自官方 Maven 1.0.8 AAR，包含 arm64-v8a、armeabi-v7a、x86、x86_64。未使用原 APK 的反编译代码或签名。

当前官方 `libxmax_yuv.so` 未做 16KB 页对齐，16KB 页 Android 设备需重编该库后验证。SDK 未透传所有摄像头热拔异常；外接 USB 摄像头取决于大屏系统和 RTC 支持，必须实机测试。尚未用真实凭证验证云端生成和弱网效果。

Android 9 / WebView 69 模拟器可验证离线手势脚本与原生界面边界，但官方 RTC 所需的 `libbytenn.so` 没有 x86_64 版本，不能用该模拟器完成真实摄像头 RTC 验收；这项限制不等同于 ARM 大屏的运行结果。
