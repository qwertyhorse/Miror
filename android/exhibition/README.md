# OpenBuy 展会试衣镜 Android

应用版本 **0.6.23 / versionCode 39**，包名 `ai.openbuy.exhibition`。提供「安卓摄像头」和「局域网电脑」两种视频来源。选择局域网电脑后，安卓直接进入原生显示端；电脑负责采集、手势与 XMAX 连接；安卓接收视频并保留原生操作，或全屏显示电脑网页。保留的安卓摄像头模式按设备能力启动：WebView 111 及以上打开最新 V1.1 网页，旧 WebView 进入原生 XMAX 镜端。

## 安装使用

1. 安装 `openbuy-exhibition-0.6.23.apk`，需要 Android 9 或更新版本。安卓摄像头模式需要摄像头权限；局域网电脑显示模式不使用安卓摄像头或麦克风。WebView 74 设备自动使用原生兼容入口，无需升级系统 WebView。原安卓入口支持 XMAX；Decart 仍需 WebView 111 及以上。
2. 首次显示四位绑定码，在 V1.1 工作人员后台绑定对应智能镜。同签名覆盖升级沿用原来的安装身份与绑定；不同构建机的 debug 签名不能直接覆盖旧包。
3. 在后台配置该镜的供应商密钥与素材，点击“开始体验”才启动生成。永久密钥不写入 APK。

默认镜端为 `https://xuxin.local:10202/v1.1/exhibition/screen`，后台为 `http://xuxin.local:10101/`。大屏和 Ubuntu 后台电脑须在同一局域网，云端生成还需互联网。电脑视频源与网页随后台更新，原生显示端随 APK 更新；服装与后台设置仍实时同步。原安卓摄像头模式的 Linux 手势服务随后台更新。

网页入口长按左下角“设备”、原生入口长按 Logo 可修改镜端网址。原生入口通过系统 DNS、局域网 NSD 服务和已有备用 IP 解析后台；Ubuntu 同时广播 `xuxin.local` 地址和 `Miror-xuxin` 服务，避免与原 Mac 冲突。默认地址迁移保留镜编号，自定义地址不变。HTTP 10101 与旧 HTTP 10200 镜端地址自动使用同主机 HTTPS 10202。

debug 包仅对指定局域网域名信任随包 CA 公钥，不跳过 TLS 或主机名验证。后台重建 CA 后需重新打包。直接使用 IP 地址时，证书仍须包含该地址，且设备需信任对应 CA。

## 电脑视频源

1. 将摄像头接到电脑，在 `http://xuxin.local:10101/` 打开对应智能镜，点击「电脑视频源」。入口为 `https://xuxin.local:10202/v1.1/exhibition/computer?mirror=镜编号`，后台按钮会自动带上正确镜编号。使用支持摄像头与 WebRTC 的电脑浏览器，允许该 HTTPS 页面使用摄像头；「电脑摄像头」中可选择设备。
2. 先停止体验，在安卓原生镜端长按 Logo，进入「设备设置 → 视频来源」，选择「局域网电脑」并保存。设备绑定、素材与皮肤继续沿用；以后启动直接进入电脑显示模式。切回「安卓摄像头」可恢复原模式。
3. 保持电脑视频源页面运行，等待安卓显示电脑画面。触摸选衣、开始、停止等操作仍在安卓大屏完成，电脑接收同一后台状态并执行。连接与预览不会启动 XMAX 生成，点击「开始体验」才开始。

「电脑摄像头 → 摄像头方向」提供默认、顺时针 90°、180°、逆时针 90°，「摄像头画质」提供 1080p / 4K。摄像头、画质与方向按当前浏览器、当前智能镜保存，刷新后恢复。停止体验后可修改；「发送到大屏」显示当前摄像头或生成画面的实际发送分辨率和帧率。旋转后的流用于本地预览、手势和 XMAX 输入；竖向 4K 预览发送横向原始视频，由安卓按方向元数据旋转显示，不在安卓复制或转换像素。生成结果不再旋转。当前 Chrome 使用摄像头帧直接驱动旋转，切到其他标签页仍能继续供屏；不具备逐帧 API 的浏览器使用前台预览兼容路径。

使用手势时，电脑视频源页面需保持前台；切到其他标签页会暂停手势识别。

电脑浏览器负责摄像头采集、手势推理和 XMAX 云端连接，并将摄像头预览或生成画面编码后，通过局域网 WebRTC 发给安卓。此模式下安卓不采集摄像头、不运行手势推理、不创建 XMAX 会话，也不上传音视频。图片输入的待机画面由安卓显示素材图；生成画面仍从电脑传来。

4K 选项控制摄像头采集和局域网预览，不覆盖 XMAX Web SDK 的默认上行编码配置；当前竖向输入默认配置为 832×1504，实际云端上行须通过 SDK 统计另行确认。

电脑模式默认 1080p，可选 4K，目标 30 帧/秒；优先使用 H264，1080p / 4K 编码目标上限分别为 6 / 24 Mbps。4K 请求摄像头原生 3840×2160，低分辨率输入不会放大；云端生成的分辨率由输出流决定。安卓以硬件解码优先的方式显示，Surface 根据实际输入像素分配，最高为 3840×2160 像素，1080p 输入仍按 1080p 预算渲染。电脑视频编码、网络接收及安卓解码和显示仍会消耗性能，并非零开销。电脑与安卓需持续在线；长时间失联后需重新连接，再由用户开始体验。

0.6.16 在当前目标大屏的 1080p 原始预览稳定后约 **30 帧/秒**，旋转预览约 **28.6 帧/秒**，电脑源切到后台标签页后约 **29.8 帧/秒**；确认使用 **H264 硬件解码**，安卓未打开摄像头。摄像头和逆时针 90° 的配置已验证刷新保留。这是当前设备与网络下的预览结果；**电脑模式的真实 XMAX 云端生成尚未完成端到端验收**。

## 无线投屏完整网页

0.6.21 的「局域网电脑」接收端同时支持完整网页无线投屏。后台点击「无线投屏」，在电脑 Chrome 中选择共享当前试衣标签页；摄像头、选款、开始、停止和手势仍由电脑处理。安卓按原比例显示完整网页，隐藏原生试衣控件，不裁掉网页边缘，也不再次旋转或镜像。该模式不回传镜面触摸。0.6.22 起只有安卓首帧实际呈现并确认后，电脑才允许开始体验。

开始共享只显示网页与摄像头预览，点击网页「开始体验」才生成。停止共享或视频连接中断后恢复连接界面，旧画面不作为有效投屏保留；恢复后需要电脑重新共享。长按完整画面或按系统返回键可打开设备设置。旧 APK 不声明网页接收能力，网页会提示升级，不将完整网页发到旧版的局部视频区域。

以下采集分辨率、画面方向、XMAX 输入方向和 Linux 手势设置适用于保留的安卓摄像头模式。

## 安卓摄像头模式：采集分辨率

0.6.12 对已实测失败的 Android 11 Droidlogic ZC-H982（t982_ar301）固件及摄像头组合屏蔽 3840×2160 采集，并兼容回退旧的 4K 配置；其他设备仍按能力提供 4K。该固件虽报告 4K，实际 NV21 采集会触发 HAL `-38` 并可能卡住系统摄像头服务；已经卡住时需重启设备。设置中切换采集档位失败且相机已正常释放时，恢复同一摄像头上一次验证成功的档位一次；取消、关闭或释放失败时不再重试。

0.6.5 原生入口增加「设备设置 → 采集分辨率」。先停止生成，长按 Logo，选择摄像头及分辨率，预览成功后保存。下拉框只列出该摄像头通过 Android 系统报告的支持档位，支持时可选 **3840×2160 · 4K**；默认「自动」优先选择 1080p 范围内最大的可用尺寸，仅支持更大尺寸时选择其中最小档。无法读取能力时沿用 704×1280。

预览状态显示 RTC 返回的「实际」采集宽高；驱动降档时同时显示请求尺寸。配置保存在本机，覆盖升级及会话重连保留。切换摄像头后，如果已选分辨率不再支持，会提示重新选择。0.6.15 根据该摄像头的 AE 帧率范围和所选精确宽高对应的最短帧周期，选择最高 30 帧/秒的采集请求；不会借用其他摄像头或转置尺寸的能力。任一元数据缺失或无效时保留兼容的 24 帧/秒，并继续遵守已知的更低能力上限。实际帧率由摄像头、驱动与设备负载决定。

采集与模型编码尺寸、帧率独立：模型输入默认请求仍为 **1024×1920 @ 24 帧/秒**，连接前继续按实际画面比例选择模型支持的横竖尺寸，编码请求帧率保持 24。4K 原始画面用于采集，发送给 XMAX 前仍根据实际画面比例，按当前模型支持的像素数及 32 倍数规则缩小。4K 采集不代表模型以 4K 生成。实机须核对「实际 3840×2160」并检查预览、生成和手势同时运行的流畅度。

## 安卓摄像头模式：画面方向

先停止生成，在原生镜端长按 Logo，进入「设备设置 → 安装方向」，选择默认、顺时针 90°、旋转 180°或逆时针 90°。调整时直接查看摄像头预览，人物朝上后保存，再开始体验。取消不保存；方向保存在当前安卓设备，覆盖升级保留。后台打开的「摄像头检测」也提供相同选项。

预览与模型输入共用此安装方向。修正在 RTC 采集端设置，发送视频沿用同一角度。手势抽样沿用 RTC 帧的旋转信息，避免重复旋转。图片输入模式不应用摄像头角度。旋转与旧设备传感器信息的实际组合仍须在对应大屏验收。

0.6.2 根据 RTC 返回的实际帧宽高和旋转信息确定相机输入比例，并在连接前统一编码和生成请求尺寸，修正此前旋转后仍使用固定竖向尺寸的遗漏。不会再次旋转生成结果。验证时需同时检查原始预览与生成画面中的人物比例，覆盖默认、90°、180°和270°；本地回归与构建不能替代具体安卓大屏的摄像头和云端生成验收。

0.6.3 在相机采集与 XMAX 编码之间增加方向适配：按校正后的实际宽高选择 RTC 固定横向或竖向模式，让 SDK 在编码前处理旋转并将旋转标记归零。每次重新采集先恢复自适应模式以读取真实尺寸，图片和视频文件输入会清除相机方向校正。该适配沿用设备设置中的安装角度，不会根据人物动作自动猜测或改变方向。

## 安卓摄像头模式：旧方向设置迁移

升级时移除旧「XMAX输入方向」设置。原先跟随摄像头或两项相同的设备直接保留安装角度；两项冲突时暂停开始体验，提示进入设置校准。工作人员检查本地预览、调整安装方向并保存后解除提示；取消或预览失败不会解除。该本地预览不能证明远端编码或生成画面方向正确。

现场验收须使用四角不同标记的非正方形画面，覆盖 0°、90°、180°、270°和前后镜像，核对实际接收解码像素、rotation 与模型宽高。JVM 回归覆盖像素转换、尺寸和 RTC 参数；无物理设备时不宣称编码像素或 XMAX 接收已验收。

## 安卓摄像头模式：手势识别

原生入口「设备设置 → 手势识别」现提供「关闭」与「Linux电脑」。原先保存为「安卓本机」的设备升级后按关闭处理，不初始化本机识别器、不抽取手势帧，也不自动改为 Linux 上传。关闭状态重启后保留；原来使用 Linux 的设备保持原设置。本机实现代码保留以便恢复。

在原生入口长按 Logo，可调整“手势识别”。选择会保存在本机，设备绑定不变。应先停止体验再切换模式。

| 模式 | 识别位置 | 额外局域网传输 | 主要验收点 |
| --- | --- | --- | --- |
| Linux 电脑 | 电脑上每设备独立的 MediaPipe CPU 人体、手部模型及 V1.1 检测器 | 原始 I420 帧；安卓不缩放、不转 RGB、不做 JPEG 压缩。电脑按后台 480/720/960 像素（默认 720）处理；抽样上限 5–30 帧/秒（默认 15） | 主画面流畅度、网络负载、手势时延和恢复 |
| 关闭 | 不运行手势识别 | 不抽取或上传手势帧 | 摄像头预览与手动选衣 |

Linux 识别复用 RTC 捕获的画面，不占用第二路摄像头。主视频、云端生成画面和音视频连接均不经过 Linux 转发。Linux 手势帧仅在内存中处理，不保存画面；每台设备最多一帧在途，后来的繁忙帧直接丢弃，不补发。新连接或重试后先收手，避免仍举着的手被当成新动作。

0.6.9 起网页、Linux 和安卓本机共用同一规则：两只手入镜时分别识别，任一只符合已启用的手势即触发一次；两只同时符合也只触发一次，持续举着不重复。人体未检出、手腕归属不明或多人入镜不会单独否决有效手势。Linux 与网页的人体姿态仍可辅助判断下放；安卓本机保留仅手部模型，通过握拳或收手观察释放。

所有手均未检出并持续达到收手时长（`palmReleaseMs`，默认500ms）后自动复位，不依赖人体姿态是否仍在或变化；短暂漏检不会立即重触发。

Linux 侧需先按 [运行时说明](../../runtime/gesture/README.txt) 安装隔离 Python 环境，然后沿用 `miror-preview.service` 启动服务。默认最多两路识别会话。安装依赖不修改系统 Python，也不需要 XMAX 密钥。Linux 模式故障时显示简短的手势重试入口，手动选衣仍可用；不会暗中切换模式而影响对比结论。

## 最新镜端行为

- 0.6.23 将电脑视频尺寸与显示缓冲区的像素预算一起更新，避免分辨率变化时先分配旧比例的中间缓冲区，再次分配正确尺寸。保留 4K、方向、视频铺满和网页完整显示。此项减少显示缓冲区抖动，不代表修复所有退出或重连原因。
- 0.6.22 在完整网页首帧实际绘制、原生控件隐藏后向电脑确认，电脑收到当前投屏批次的确认才显示已投屏并允许开始体验。迟到帧、已停止共享和旧连接的确认不会激活新批次；旧 APK 缺少首帧确认能力时提示升级。

- 0.6.21 增加完整网页无线接收，保留原有电脑视频模式；网页按比例全屏显示，断线或停止共享时清除最后一帧并恢复连接状态。

- 0.6.20 暂停后回到初始取景布局，统一显示「开始体验」，点击后恢复当前选择，不另起重叠会话。旧会话尚未释放时显示「正在清理…」并禁用启动；真实摄像头、网络或清理故障继续提示。网页电脑源和安卓两种显示模式保持一致，暂停时仍沿用原有素材选择及摄像头校准锁。
- 0.6.19 合并自动素材目录 `catalog-v2` 与内容版本校验，统一摄像头安装方向并迁移旧冲突配置；保留 XMAX 1.0.9 的区域模型、原始手势帧、电脑显示与 4K/H264 支持。

- 0.6.18 电脑显示端按 Android 芯片实际 H264 Baseline 能力补充普通 Baseline 协商，与 Mac Chrome 的硬件编码规格兼容；不满足能力要求时保留原有接收规格。电脑源增加编码器、编码耗时、CPU/带宽限制及网络统计诊断，便于区分 4K 采集、局域网发送和云端生成。
- 0.6.17 电脑源增加可保存的 1080p / 4K 画质配置及实际发送规格。竖向 4K 预览采用横向传输、显示端旋转，适配最高解码高度为 2160 的硬件；Surface 随输入尺寸调整，支持切回 1080p。
- 0.6.16 增加电脑采集、手势和 XMAX 连接，经局域网 WebRTC 向安卓显示端传送视频；安卓保留原生触摸控件。显示模式不初始化安卓摄像头、手势模型或 XMAX 连接，使用独立的视频接收器，首张画面实际绘制后才报告就绪。视频来源选择保存在设备上，覆盖升级保留。
- 0.6.15 RTC 帧观察器使用默认像素格式，不再强制每个相机帧转换为 I420；仅在真正抽取手势帧时转换并复制为紧密 I420。采集帧率按选定摄像头及尺寸的能力最高请求 30，模型与编码仍请求 24；Linux 手势继续发送未经缩放、RGB 转换或 JPEG 压缩的原始帧。
- 0.6.14 主页面本地摄像头改用独立 SurfaceView 显示层，远端视频保留 TextureView 的首帧切换。视频渲染表面限制为 1920×1080 的像素总量，并按原比例铺满舞台；设置小预览、摄像头采集、手势原始帧和 XMAX 编码尺寸独立。未使用的轨迹层不参与布局或绘制，透明轨迹位图只在实际画轨迹时分配。此限制减少 4K 大屏的渲染工作，不对传给电脑的原始帧缩放或压缩。
- 0.6.13 暂停安卓本机手势识别，并将电脑识别路径改为原始 I420 传输，安卓不再执行手势缩放、RGB 转换或 JPEG 编码。

- 0.6.11 升级 XMAX Android SDK 1.0.9，原生端按区域使用 X2.1.1 Preview；后台保留网页端原有模型与路由，保留设备绑定和素材。
- 0.6.10 修复 Android 11 原生入口启动闪退：全屏设置先创建窗口 DecorView，窗口尚未附着时使用兼容系统栏设置；网页入口复用同一逻辑。
- 0.6.9 统一双手识别：任一只手符合即触发，两只同时符合只执行一次。安卓本机需安装新 APK 才能更新内置检测器；设备绑定和识别模式保留。
- 0.6.8 将 Linux 手势抽样尺寸、帧率、收手及再次抬手提示与网页对齐，新后台兼容旧 APK 并提供人体姿态识别。
- 0.6.7 将体验中的停止操作移至视频下方边框，与手势状态并排显示为小方块图标；正在停止时禁用。开始、继续及恢复操作保留原位置。
- 持续展掌只换一次，收手后再抬手才能再次触发。
- 命令提交、素材准备、连接与服务端生成期间丢弃手势，不排队、不补执行；有效收手仍用于解除手势锁定。
- 点击选衣、翻页笔方向键和后台选衣仍可使用；手势忙碌拦截不会取消手动操作。原生 SDK 条件更新保持串行。
- 收到服务端切换确认后恢复手势；SDK 没有逐套服装画面完成信号，实际画面可能稍后更新。
- 安卓摄像头模式的网页与原生入口保留摄像头选择、后台远程检测、素材抽屉与皮肤。旧设备从 RTC 已捕获的画面抽样，不另开第二路摄像头；最多检测两只手，两种识别模式均逐手判断并共用动作防重复锁。
- 0.6.13 的 Linux 路径发送原始 I420 帧，电脑执行方向修正、颜色转换与缩放；不回退安卓 JPEG 压缩。后台须配套升级并声明 `i420-v1` 能力。电脑处理长边与抽样帧率沿用后台配置；原始传输最大支持 3840×2160 像素总量。1080p 每帧约 3.1 MB，采集、复制和网络发送仍会消耗安卓性能；传输繁忙时减少实际抽样，不积压帧。更改抽样设置立即使旧帧失效，不影响 XMAX 主视频采集或编码。繁忙帧和超过 800ms 的迟到结果直接丢弃，实际帧率取决于设备与网络。
- 原生安装身份通过同源接口提供给镜端，网页不持有永久供应商密钥。设备自启动、系统 kiosk 和 USB 驱动由大屏系统配置。
- 原生端与网页端共用服务端 `catalog.looks` 可用目录和 `catalog-v2` 协议。开始与换装只提交素材 ID、内容版本及操作身份，由后台解析并绑定持久引用；原生端不再做 1.5 秒准备预查或重复绑定。目录更新即时反映在可选列表，`activeLook` 保持正在使用的旧版本，直至下一次选择。旧后台缺少目录时明确提示升级；网络、素材未准备、版本变化和供应商错误保留各自错误类型与原因。MoX 仅下载本地原图作为输入画面。
- 续接先取得后台计划，再释放旧 RTC 和确认旧凭证停止，最后提交续接。取得计划前的临时网络错误或素材切换冲突保留当前画面，在后续心跳重试；租约与凭证硬到期仍独立约束连接。

## 构建与验证

需要 JDK 17、Android SDK 37.0、build-tools 36.0.0。项目使用 AGP 9.1.1、Gradle 9.3.1，minSdk 28、targetSdk 35。

```sh
# 在仓库根目录，使用项目 Node.js 运行时生成并核对共享手势脚本
node scripts/build-android-gesture.mjs
node scripts/build-android-gesture.mjs --check
cd android/exhibition
sh scripts/build-local.sh assembleDebug lintDebug --max-workers=2
sh scripts/test-native.sh
```

`build-local.sh` 仅为当前进程设置工具链路径，不改全局 shell，不自动接受许可。默认兼容 Mac 工具链与 Ubuntu 的 `~/.local/share/openbuy-android/{jdk-17,sdk}`，也可设置 `JAVA_HOME`、`ANDROID_HOME`、`GRADLE_USER_HOME`。

输出 `app/build/outputs/apk/debug/app-debug.apk`。debug 签名由构建机的本地 keystore 决定；覆盖旧包需要相同签名。正式发布需另行配置长期签名，不应卸载已有绑定的包来绕过签名不匹配。

局域网下载文件放在仓库 `public/downloads/`，每个版本保留独立文件名。当前 Mac 测试大屏使用独立包名 `ai.openbuy.exhibition.android11test`，对应 `openbuy-exhibition-0.6.23-android11-mac-surface.apk`（versionCode 39）；该构建副本默认连接 `xuminghong.local`，debug HTTPS 信任域名也须为 `xuminghong.local`，随包 CA 须与 Mac 运行证书一致。主源码仍保持 Ubuntu 默认入口。升级前核对已安装包名、版本号和签名；使用同包名、同签名且更高 versionCode 的 APK 执行 `adb install -r`，保留安装身份、后台绑定、视频来源和摄像头设置，不卸载或清除数据。覆盖安装会关闭应用，安装后须重新打开并确认后台在线、原绑定及画面恢复。普通包与 Mac 测试包不能互相覆盖。

原生 JVM 测试使用隔离网络与供应商替身，不消耗真实额度，覆盖原生流程、上传所有权、帧过期、迟到结果和 NSD。电脑视频接收器另覆盖信令 epoch、提前到达的 ICE、首帧状态、断线恢复、渲染尺寸和资源释放；这些替身测试不代表实际解码性能。网页手势集成测试使用真实检测器、Hook 和 Kiosk，仅模拟摄像头推理和网络。`tests/nativeGestureRuntime.test.ts` 同时校验 APK 内脚本与当前 TypeScript 源码完全一致；旧 Chromium 和 Android 的验证见 [手势运行时](docs/native-gesture-runtime.md)。服务端协调器、HTTP 边界和真实模型分别有隔离测试，模型性能结果不包含安卓编码与局域网往返时间。真实摄像头、云端生成和弱网恢复仍须在对应模式及目标设备上验收。

`uiPreview` 仅用于静态界面截图，包名后缀 `.uipreview`，不作为摄像头、手势或云端生成的验收结果。

全屏启动回归须在 Android 11/API 30 上运行，覆盖 `setContentView()` 前尚未创建 DecorView 的真实系统窗口；另从 `MainActivity` 冷启动，检查原生界面和返回前台时无崩溃：

```sh
sh scripts/build-local.sh assembleDebug assembleDebugAndroidTest --max-workers=2
# 指定隔离模拟器，不在已绑定展会设备上运行 instrumentation。
adb -s "$EXHIBITION_TEST_SERIAL" install -r app/build/outputs/apk/debug/app-debug.apk
adb -s "$EXHIBITION_TEST_SERIAL" install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
adb -s "$EXHIBITION_TEST_SERIAL" shell am instrument -w -e immersiveOnly true ai.openbuy.exhibition.test/ai.openbuy.exhibition.NativeGestureInstrumentation
```

## 保留的原生 SDK

官方来源：https://github.com/XingMai/XmaxSDK-Android ，固定 commit `696852c61a6b403dd904e8eb91fd8a302c7802b6`。MIT 许可证保留在 `vendor/xmax-sdk/LICENSE`，`UPSTREAM.json` 记录源码和 JNI SHA-256。

SDK 源码调整国内/国际两个 API 根地址，并补充 RTC 摄像头枚举和按设备 ID 选择；具体差异见 `vendor/xmax-sdk/LOCAL_CHANGES.md`。XMAX SDK 为 1.0.9，底层使用 Agora 4.6.4；JNI 来自官方 1.0.9 Release AAR，包含 arm64-v8a、armeabi-v7a、x86、x86_64。未使用原 APK 的反编译代码或签名。

局域网电脑显示模式使用 `io.getstream:stream-webrtc-android:1.3.10` 接收视频，不初始化上述 XMAX/Agora 连接。Stream 的 Apache 2.0 许可证、WebRTC 的 BSD 许可证及附加专利授权保留在 `app/src/main/assets/third-party-notices.txt`。

当前官方 `libxmax_yuv.so` 未做 16KB 页对齐，16KB 页 Android 设备需重编该库后验证。SDK 未透传所有摄像头热拔异常；外接 USB 摄像头取决于大屏系统和 RTC 支持，必须实机测试。尚未用真实凭证验证云端生成和弱网效果。

Android 模拟器可验证离线手势脚本与原生界面边界；真实摄像头采集、旋转和 RTC 生成须在目标大屏上验证。
